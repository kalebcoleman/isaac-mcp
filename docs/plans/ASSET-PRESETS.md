# Plan: USD asset presets and project-folder discovery

**Status: proposal, not shipped.** On 2026-10-31 the owner chose a trusted-operator loader (operator-approved folders, bundled samples and the NVIDIA cloud library, in the normal session) as the first step. Draft [PR #11](https://github.com/kalebcoleman/isaac-mcp/pull/11) implements the trusted project-folder part; bundled samples and the cloud library are milestone M6 of [SIM-TOOLS-FOLLOWUP.md](SIM-TOOLS-FOLLOWUP.md). None of these is a sandbox; the isolated loader below remains future work. This plan covers generic scenes, robots, objects and small smoke fixtures, not full separate projects. Evidence labels: **Code** = static repository inspection at the base revision; **Package** = read-only inspection of the installed Isaac Sim 6.1.0 tree/stubs, not a running app; **Source** = cited vendor documentation; **Assumption** = design choice or behavior requiring validation. No Kit process was launched for this plan.

The [end-to-end asset and scene plan](ASSET-SCENE-END-TO-END.md) combines this work with generic scene tools and
proposes a separate user-trusted workflow. This document's isolated, fail-closed restrictions still apply to
untrusted assets; its historical PR sequence and pre-merge code observations should be rechecked against current main.

## Starting point and integration

- **Code:** `exts/ur5e-dt/ur5e_dt/extension.py`, `MCP_TOOL_REGISTRY`, `load_workstation`, `load_simple_room`, `add_objects`, `quick_start*` and `setup_camera_tf_graph` implement specific twin workflows, not a generic catalog. The workstation references an operator-supplied or cached `workstation/vention.usd` (falling back to a placeholder bench); the room uses `get_assets_root_path()` and may resolve to local or cloud storage. `add_objects` enumerates selected assembly folders and treats `_physics` USDs as overlays; camera setup also creates a graph and attaches to a specific wrist. Those behaviors cannot all be represented by a single raw USD reference.
- **Code:** `isaac_mcp_bridge/builtins.py`, `cmd_put_file`, `cmd_get_file` and `cmd_stat_file` expand and absolutize paths with no root, extension or explicit byte cap; `cmd_put_file` can overwrite. `run_python` can load arbitrary USD and execute arbitrary Python. A user may also arrange files through the local filesystem or another transfer channel; these built-ins are not the only possible way files reach Kit. `docs/TOOLS-HOST.md` describes their trust limits.
- **Code:** [generic sim design](../GENERIC-SIM-TOOLS.md) is unimplemented. Its `prim.create(reference=...)`, local-only allowlisted references and deletion/output safety rules are the starting conventions. This plan extends its asset discovery/metadata and **supersedes its proposed path-only reference safety rule**: all future `sim` reference and asset-valued attribute entry points must use the same isolation, immutable snapshot and dependency policy below, or refuse untrusted inputs. Preserve its `on_conflict="error"`, absolute prim paths and explicit deletion confirmation. Do not imply those draft tools exist.

## Registry and surface

**Recommendation (Assumption):** a sibling Kit-side extension `exts/asset-tools`, registered as owner/namespace `assets`, sharing the existing bridge; canonical `assets.scan` becomes MCP `assets__scan` (see `mcp/isaac_mcp/server.py`, `_mcp_name` and `register_dynamic_tool`). USD access belongs near the stage, while path policy and manifest validation should be a stdlib-only library importable without Kit. A host-only pack cannot reliably inspect the remote Kit filesystem or stage. Extending `ur5e_dt` would impose twin dependencies on generic users; putting all of this in `sim` ties an independently useful catalog to an unbuilt pack. Share the policy with `sim`, not a second importer.

Use versioned, small JSON manifests (stdlib parser; no YAML parser or executable Python registry). One manifest per preset under the extension's packaged preset directory, plus optional `presets/*.json` under each **user-configured** root, including a folder in the user's project checkout. User manifests remain user-controlled data; they are not committed to the isaac-mcp repository as part of this project. Root IDs are administrator-defined opaque labels; relative paths never select a root by absolute path. Reject unknown schema versions, duplicate qualified names, invalid fields and paths, unsupported values, missing license/provenance and conflicting entries; no silent user override of bundled entries. Qualify names, e.g. `project:workstation`, `project:fixture`; list source and availability. Manifest text is untrusted metadata, not executable configuration.

| Field | Required v1 contract |
|---|---|
| `schema_version`, `name`, `file` | integer `1`; unique qualified identifier; relative `.usd`, `.usda`, or `.usdc` file beneath its root |
| `default_prim` | expected absolute prim path or `null` with explicit explanation; compare to inspected value |
| `up_axis`, `meters_per_unit` | expected `Y`/`Z` and positive finite number; unknown is explicit and blocks automatic normalization |
| `kind`, `physics_readiness` | `robot`, `scene`, `object`; `visual_only`, `authored`, or `unknown`, with evidence/notes, never a guarantee |
| `tags`, `source_isaac_sim_version` | bounded strings; version or `unknown`; no implied compatibility |
| `license`, `provenance` | SPDX identifier or explicit license reference/permission, attribution and source/version; `unknown` blocks redistribution, not necessarily local user use |

**Code + recommendation:** Describe the workstation as an object/visual preset with source units recorded after inspection, retaining its existing twin wrapper separately; its handler comments describe centimeters and visual-only handling, not verified manifest metadata. `ASSEMBLIES` maps multiple folder files plus JSON configurations and physics overlays: catalog each independently eligible object only after dependencies and licensing are checked, and model assembly composition separately rather than claiming a folder is one USD. `load_simple_room` may use a network asset root, so it is **not** eligible until a licensed local copy and all dependencies pass the same policy; otherwise show unavailable with a reason. Robot, gripper and sensor assets are candidates after provenance and safety review, while `quick_start*` and camera graphs remain workflows, not asset presets. Do not copy assets or migrate twin callers in the first catalog PR.

Proposed tools (all new, no existing name changes):

| Canonical name | Contract |
|---|---|
| `assets.list` | bounded, paginated manifest names, kind, source and availability; no stage change |
| `assets.info(name)` | bounded metadata, validation state and warnings; no stage change |
| `assets.scan(root_id, relative_dir="", cursor=null)` | explicit bounded discovery of user USD files; details below |
| `assets.load(name, prim_path, pose=null)` | validate and load approved preset into an isolated Kit stage, default conflict error; return actual path, snapshot ID, checks, warnings and observed effects |
| `assets.import_usd(root_id, relative_path, prim_path, pose=null)` | identical pipeline for a discovered user file, no implicit registration or path escape |

Use absolute validated USD prim paths, pose `{position:[x,y,z], orientation:[w,x,y,z]}` in stage units/meters as explicitly specified by the eventual contract; reject nonfinite numbers and bad quaternions. Return structured `status`, stable error code, actionable message, warnings and actual effects; no automatic overwrite. `list`, `info`, `scan` are intended read-only/idempotent; load/import mutate the isolated stage, are non-destructive only with conflict refusal, and are not automatically idempotent. Set accurate MCP `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint` after behavior is verified; hints do not enforce policy.

**Code:** PR #4's `origin/feat/host-tool-scoping:mcp/isaac_mcp/local_tools.py` groups only host-local gateway, screen and Isaac Lab tools; `ISAAC_MCP_LOCAL_TOOLS` does not scope bridge tools. `ISAAC_MCP_NAMESPACE` filters the discovered `assets` namespace and `ISAAC_MCP_BUILTINS=0` hides bridge built-ins from the host view. Do not add `assets` to local groups unless a future **host-local** tool is actually introduced; if so, give it a group and annotations using that PR's model. Bridge `ToolDefinition`, `get_registered_tools` and host `register_dynamic_tool` currently do not carry MCP annotations; a separate backwards-compatible bridge protocol/host change must transport and test them, with unknown metadata safely handled. PR #4 is under review, not a dependency or shipped behavior at this base. Neither groups nor hints are a sandbox.

## Project-folder discovery

### Is it safe?

**Recommendation:** only as a constrained, explicitly enabled workflow with runtime isolation and verification, not as a guarantee that hostile USD is safe. A root allowlist and pre-load scan alone are insufficient: USD resolvers and file-format plugins can access resources *while inspecting*, unexpected code can run through enabled extensions, resource exhaustion is possible, and paths, file contents and resolver context can change after validation. OS isolation, immutable inputs, controlled plugins and script execution, bounded resources and fail-closed checks are required for both inspection **and the entire load/use lifetime**. Even then native parser, GPU/driver and sandbox vulnerabilities remain residual risks; use a separate low-privilege account/container or VM for adversarial material. An ordinary unrestricted existing Kit process cannot be made safe merely by checking a path; the untrusted profile must refuse import there if enforcement cannot be verified.

### Approval, discovery and limits

The user configures `ISAAC_MCP_ASSET_DIRS` **on the Kit bridge machine** before launch, e.g. a platform path-separated list of existing directories with admin-assigned root IDs. Default empty disables user discovery and import. An agent can select an already configured ID but cannot add, widen, change policies or resolve arbitrary absolute paths at runtime. A user approves a folder by editing the launch configuration outside the tool interface and restarting the isolated service; clearly display root IDs and scope to the user. A user-selected root may be inside the user's own project checkout, including a local folder in a repository, or outside a checkout; apply the same root, dependency, isolation and access controls in either case. Do not commit personal/user assets or manifests to the isaac-mcp repository. Resolve configured roots at startup, reject invalid, overlapping/ambiguous roots and filesystem roots by default, and do not silently expand access. A broad folder exposes its file names and approved data to the agent: configure the narrowest project folder.

`assets.scan` is requested explicitly, never a background watcher. Enumerate with bounded directory handles, do not follow symlinks, accept only regular files with `.usd`, `.usda`, `.usdc` (case-insensitive); reject absolute input, URL schemes, `..` components, special files, and links escaping a root. Prefer Linux `openat2`-style beneath/no-symlink resolution or equivalent tested descriptor-relative operations; canonical `realpath` plus `commonpath` is useful defense but is **not** race protection. No `.usdz` in v1 until archive traversal, size expansion and packaging rules are separately designed. Local relative paths may resolve to another file only under a configured root and the active dependency policy; reject `file://`, `http(s)://`, `omniverse://`, other schemes, absolute paths and unresolved identifiers even if a resolver might interpret them locally. Check every layer, payload, reference, texture and other asset-valued dependency, including transitive, variants, clips and plugin-specific forms; if complete enumeration cannot be demonstrated, classify as unknown and refuse to load.

Proposed configurable **hard upper bounds**, not performance claims: 256 MiB per file, 1 GiB total candidate/snapshot bytes, 10,000 directory entries visited, 1,000 candidate USDs, directory depth 8, dependency depth 16, 2,000 dependency files and 100,000 inspected prims. An admin may lower limits, not an agent. Enumeration must count all entries including non-USD and symlinks, stop at the first exhausted budget or deadline, page deterministically with a bounded cursor, and return `truncated`/reason rather than silently declaring a partial scan complete. A per-scan CPU, memory and wall-clock limit is enforced on an isolated worker (propose 60 seconds and 2 GiB initially; tune from measurements). USD parsing may expand before prim counts are available, so OS resource limits are mandatory. Unknown, malformed, over-budget, unreadable or incomplete means `not_loadable`, not a warning-only success.

Each result includes a sanitized display name, root ID, relative path, bytes, snapshot/inspection status, default prim, up-axis, meters-per-unit, dependency result and bounded reasons, and a physics-readiness **hint** (`unknown` if not safely established). Report authored vs fallback metadata and capped/truncated counts; no false claim of inspection when only a filename was enumerated. Escape control characters, cap each untrusted string (e.g. 256 UTF-8 bytes) and total response (e.g. 64 KiB), omit documentation/customData by default, never interpret embedded instructions, and label all file/prim text as untrusted data. Escaping does not eliminate prompt injection. Paginate rather than include full USD content.

### Inspection, immutable snapshot and load

1. A broker opens candidates relative to an approved root without following symlinks; safely copies the bounded candidate working set, including any potential companion files, into a private, quota-limited snapshot with preserved relative layout. If the working set cannot fit the file, entry, depth or byte budgets, refuse inspection rather than snapshot a silently incomplete tree. Source may change during copying: the exact copied bytes, not the original path, are the input; reject read/size errors and changes detected during copy. Avoid hard links to mutable sources. In the untrusted profile, no original file is parsed or loaded in an unrestricted process.
2. Launch a low-privilege, resource-limited inspection worker with only approved read-only snapshot and trusted runtime files visible, private scratch, no credentials or host home, no external network (including DNS), and a narrow broker IPC channel. Allow only verified resolver/file-format plugins and a fixed resolver context; forbid arbitrary plugin search paths. Validate that OS restrictions actually apply, including subprocesses, before opening any USD. Treat third-party plugins and drivers as part of the trusted computing base. If isolation, GPU/device access restrictions, script disabling, plugin control or dependency completeness cannot be established on a platform, return a clear unsupported error and do not load.
3. Before stage composition, inspect authored layer data and recursively inventory asset paths using an audited, bounded method. **Package:** the installed Windows 6.1.0 USD stub exports `pxr.UsdUtils.ComputeAllDependencies`, `ExtractExternalReferences` and `Sdf.Layer.GetCompositionAssetDependencies`, but gives only `*args, **kwargs`; no completeness, side-effect, signature or traversal guarantee was established. Investigate these APIs and layer asset-valued fields as candidates, not a security boundary: they may resolve/open dependencies and invoke plugins. Run even candidate scanning inside the restricted worker. Verify coverage of sublayers, references, payloads, texture paths, variants, clips, packages and unresolved identifiers against fixtures; reject unsupported/dynamic or unenumerable forms. Do not compose to discover whether it is safe to compose.
4. Default **strict mode** refuses any dependency outside the root USD file, including otherwise local dependencies, and any unresolved/dynamic reference; this is a deliberately narrow first profile. An administrator may explicitly enable a future `contained` profile for multi-file assets after the complete transitive set is proven within the configured roots and copied into the snapshot. It still rejects all network, outside-root, unsupported and unresolved references; `external` in strict mode means any separate file. Scan returns dependency counts/reasons and warnings in both profiles; a warning can never override a refusal.
5. Inspect default prim, authored/fallback up-axis and units, capped prim count and physics schemas read-only **inside isolation**, only after preflight; if composition is needed for accurate metadata, label this separately and perform it in the same isolated environment. Compare manifest expectations. Load exactly the verified immutable snapshot into a similarly restricted, dedicated Kit process whose filesystem/network restrictions remain active during later composition, rendering, timeline play and reload; reuse identical resolver/plugin configuration. Bind snapshot identity/hash and policy to the load request, prevent replacement after validation (private read-only mount with no writer; verify ownership, identity and digest), and discard it after the stage releases it. No validated path may be reopened from the mutable project folder. Never hand the snapshot to an unrestricted Kit merely because it passed preflight.

**Assumption:** a practical GPU-capable sandbox and complete plugin/dependency enforcement for each supported Isaac version remain to be demonstrated. If not, ship discovery as filename-only and mark detailed inspection/import unavailable; do not silently fall back. The first supported topology is an isolated Kit and broker on the same machine as the configured folder, including a deliberately mounted shared folder visible to that Kit. Agent-side paths are never assumed to exist on the bridge machine. Remote Kit with no shared mount requires the dedicated upload flow below; until that flow and isolation are verified, it is unsupported.

### Usability: example, follow-on and acceptance criteria

**Assumption / proposed behavior:** A user places `robot.usda`, `materials.usda` and `textures/paint.png` in an `assets/` folder inside their project checkout, configures that folder as a root on the Kit machine, and asks the agent to use `robot.usda`. Filename discovery can list the USD files within the configured root. The first loading version's strict policy must refuse `robot.usda` if it references the separate layer or texture, even though both are under the approved root; it must explain that separate dependencies are unsupported in strict mode. It also cannot load this asset into the user's already-running unrestricted Kit session: the untrusted loader requires a verified isolated Kit. A standalone USD without separate dependencies may be loadable in the dedicated isolated Kit only when every isolation and validation check succeeds. Thus the first loading version does **not** satisfy the common multi-file asset-in-existing-session workflow.

**Recommended follow-on:** first prove the opt-in `contained` profile in the isolated Kit: snapshot the complete bounded working set, verify the transitive supported dependencies under configured roots, and enforce the same filesystem, network, plugin and script restrictions for the full load/use lifetime. A contained multi-file asset can then be used in that dedicated isolated session, not automatically in an existing unrestricted session. The implementation must demonstrate coverage and enforcement on each supported platform/version; incomplete enumeration or unverifiable controls still refuse the load. This offers a useful project-folder path without treating a dependency scan as a sandbox, at the cost of a separate session and restrictions on asset formats and dependencies.

For assets the **user personally trusts**, consider these separate options; neither is an escape hatch from the untrusted profile:

- **Existing manual workflow:** the user may open their own asset through Isaac Sim's own interface in their existing session, outside this proposed agent importer. This preserves the user's familiar session but grants the asset and active extensions that session's filesystem, network and credential access; the proposed checks do not protect it.
- **Possible future trusted-session integration:** only after owner approval and a separate design/review, offer a distinct, default-off operator-configured workflow for an explicitly user-authorized asset and session. The user/operator must make the trust decision outside agent-controllable metadata or tool arguments; the agent cannot promote an asset, switch profiles, widen roots or override a refusal. Show the selected session and the loss of isolation to the user before authorization, keep audit records and existing root/size checks, and never silently fall back from the untrusted loader. An unrestricted Kit may still resolve unexpected dependencies or execute scripts/plugins with the user's privileges despite preflight or a snapshot. This option trades isolation for convenience and is **not a verified safety boundary**; scripting remains a separate explicit owner decision, not an implicit consequence of trusting a file. Until such a workflow is designed and approved, use the manual option or isolated session.

Acceptance criteria for future implementation, not claims about current behavior:

1. With an explicitly configured root such as the project's `assets/` folder, a bounded scan lists `robot.usda` by root ID and relative path whether the root is inside or outside a checkout; default-empty configuration lists no user files. The same escape, symlink, resource and access tests pass in both locations.
2. In strict mode the example's separate layer/texture yields a clear, actionable refusal and no stage mutation; a standalone eligible USD loads only into a verified isolated Kit from its immutable snapshot. Missing or unverifiable enforcement fails closed.
3. Selecting an existing unrestricted session for the untrusted loader returns an unsupported/refused result, never a silent trusted fallback. Scan and load responses distinguish listed filenames, validated assets and actual loaded stage/session.
4. Before enabling contained mode, a live isolated test loads the example with its in-root transitive dependencies and rejects outside-root, network, unresolved, changing or unenumerable dependencies; enforcement remains active through rendering, play and reload. Test failed isolation and plugin/script-control probes as hard refusals.
5. Any future trusted-session proposal separately demonstrates user/operator authorization, default-off configuration and visible risk disclosure; tests prove the agent cannot enable or select it as a fallback. This verifies workflow controls, not safety of arbitrary files in the unrestricted session.

### Scripting and trust boundaries

**Package:** in the installed 6.1.0 tree, `apps/isaacsim.exp.base.kit` declares `omni.graph.scriptnode` and `isaacsim.replicator.behavior`; the latter's `config/extension.toml` depends on `omni.behavior.scripting.core`. `apps/isaacsim.exp.full.kit` depends on base and declares `omni.behavior.scripting.bundle`. Script Node's `_impl/extension.py` has a session opt-in check and a headless path without a UI prompt; `ogn/python/nodes/OgnScriptNode.py` uses `exec`. Behavior `scripts/script_manager.py` begins with execution disallowed but can enable it based on settings/approval and invokes lifecycle callbacks. These are declarations and code paths, **not proof of effective extensions, settings or behavior** in this project's actual 5.1/6.2/headless launch. Some installed replicator extension configuration sets a script-node opt-in in its own argument settings; whether applied here is unknown. [NVIDIA's Script Node documentation](https://docs.omniverse.nvidia.com/kit/docs/omni.graph.scriptnode/latest/Overview.html) says evaluation executes Python stored in USD; [Behavior Scripting documentation](https://docs.omniverse.nvidia.com/extensions/latest/ext_python-scripting-component.html) warns that associated scripts can run with user credentials. [OpenUSD's asset-resolution documentation](https://openusd.org/25.11/glossary.html#asset-resolution) explains resolver abstraction. USD is scene data, but extensions and plugins can make opening or evaluating that data execute code.

Disable script-capable extensions and graph/behavior execution in the isolated profile, verify effective extension list and settings at startup, and refuse if a required control is unknown, mutable by the agent, or cannot be proven active for the whole session. Reject scripted/unknown executable schemas rather than relying only on a prompt or scanning node names. No agent approval may turn scripting on. An administrator-controlled trusted scripting profile, if ever built, is separate from this untrusted-import design and still needs isolation. Validate actual triggers and bypasses for installed 5.1/6.2 variants and headless mode before claiming protection.

**Code:** `run_python`, `put_file` and `get_file` already provide broad Kit-process file/code access, so a restricted asset surface is a safer intended route only when those capabilities and other bypasses are unavailable to the agent. Recommend `ISAAC_MCP_BUILTINS=0` and narrow `ISAAC_MCP_NAMESPACE`, but these are host-view filters, not socket access control. PR #4's `ISAAC_MCP_LOCAL_TOOLS` is a registration filter and annotations are hints, not a sandbox. Secure the underlying bridge, credentials, other tool packs and OS permissions; never expose its unauthenticated socket to untrusted clients. A different tool with `run_python`-equivalent access defeats this model. In the untrusted profile, the loaded scene belongs to the dedicated isolated Kit process; importing into an existing unrestricted Kit is unsupported unless that process itself meets the same verified lifetime controls. The separate, user-trusted options above have a different risk model and must not be presented as this profile.

### Remote upload

For remote users without a mounted folder, recommend a **dedicated**, separately enabled `assets.upload` to an admin-configured staging root, not relaxed `put_file`: chunked bounded transfers, random upload ID, per-user quotas, allowed relative paths/extensions (USD roots and, only in the future contained profile, explicitly permitted texture/dependency types), no overwrite, no symlinks, digest/length verification, temporary file plus atomic publish, cleanup/expiry and concurrency limits. Model multifile directories explicitly and apply the identical snapshot, dependency, isolation and script policy before any inspection/load. Authenticate and authorize the transport independently; do not infer identity from a tool parameter. Upload is not present in v1 until those controls are tested; existing `put_file` is not a safe replacement. Dedicated pack discovery works when `ISAAC_MCP_BUILTINS=0`, subject to namespace filtering; the flag does not secure a raw bridge socket.

## Units, physics and compatibility

**Code:** `load_workstation` comments describe MetricAssembler applying a centimeter-to-meter adjustment and a measured fallback when it did not; applying both scales can double-normalize. `load_simple_room` disables collision as a scene-specific optimization. These are not a generic physics validation. **Recommendation:** report source and target units/up-axis, what was authored vs fallback, observed automatic transform and any applied wrapper transform. Default to reject mismatch with a precise warning until version-specific conversion is verified; later allow an explicit conversion on an owned wrapper, never rewrite source or stack an automatic conversion twice. Physics readiness is an observation of authored collision, rigid-body, mass and articulation schemas plus missing prerequisites; distinguish `visual_only`, `authored` and `unknown`, report disabled/missing components and required stop/play or cooking, and never promise stable physics, performance or safety. Preserve stage state on failure as far as possible and report partial changes.

**Assumption:** 5.1 and 6.2 may differ in shipped asset locations, schemas, resolver behavior, extension availability, MetricAssembler and physics; compare recorded source version with runtime, warn for mismatches/unknown, missing local assets, unsupported schemas or conversions. Do not assert incompatibility solely from a version mismatch. Validate supported versions in live tests before advertising compatibility.

## Repository, tests and documentation

**Code:** the Vention workstation USD was about 58 MiB on disk; it is no longer bundled (see [provenance/ASSETS.md](../provenance/ASSETS.md)), but it shows why to avoid making a large binary the default. Keep only tiny redistributable generic USD fixtures with explicit license and provenance in Git; set a documented size budget (recommend 1 MiB per fixture, 5 MiB total). Use Git LFS or versioned release assets plus hashes/license for larger redistributable presets, subject to owner and hosting policy; do not move existing assets in this plan. Do not add personal/user assets or manifests to the isaac-mcp repository. Users may keep their own assets and optional manifests inside their own project checkouts, subject to their project's own version-control and privacy choices.

- **Off-Kit, stdlib/fakes:** manifest validation, qualified-name collisions, grouping and annotations metadata plumbing, bounded enumeration and pagination, extension/URL/path rejection, `..`, symlink and concurrent replacement races, root configuration inside and outside project checkouts, identical enforcement for both, strict example refusal and fake resolver dependency graphs (cycles, variants, depth/byte/file caps, unresolved/external paths), upload quotas/atomicity/digests, snapshot immutability, sanitization, error codes, no-side-effect-on-failure, and enforcement fail-closed cases. Inject a fake filesystem/resolver rather than importing Kit in policy tests. `isaac_mcp_bridge/schema.py` and `toolset.py` are existing off-Kit precedents.
- **Plain USD off-Kit, conditional:** if a compatible `pxr` build and plugins can be installed in an isolated worker, exercise the actual dependency APIs and small USD fixtures, including adversarial paths and incomplete scans. **Package:** this host's `python3` cannot find `pxr`; inspected installed bindings are Windows `.pyd`, so off-Kit execution, signatures, coverage and safe use were **not verified**. `pxr` without Kit is a test opportunity, not an assumed guarantee.
- **Needs live isolated Kit, not run here:** verify actual app/extension and security settings, no script execution on open/evaluation, resolver/plugin and network/filesystem enforcement under malicious fixtures, immutable snapshot under concurrent edits, strict and contained example acceptance criteria, stage composition and unit transforms, physics/cooking and timeline effects, long calls/timeouts, user-visible warnings and 5.1/6.2 drift. Test that a failed sandbox/unknown plugin/unresolved dependency cannot fall through to unrestricted Kit. Independent security review and OS-level negative tests precede enabling import.
- **Docs in implementation PRs:** add a new tool reference and correct `AGENTS.md` counts, setup/configuration and user approval examples, threat model and topology, strict versus contained policy, metadata meaning and limitations, version matrix, safe remote transfer instructions, and cross-reference/update the generic sim draft. Run `python3 scripts/check_docs.py` and CI when registered tools change.

## Recommended independently mergeable PRs

Sizes are rough changed lines including tests/docs, not promises. Each PR is useful on its own once prior merged groundwork exists; no PR relies on an unmerged branch.

1. **S (150–300):** manifest schema, offline validator, tiny licensed fixtures and documentation; no discovery or loading.
2. **M (300–600):** bounded opt-in root enumeration, filename-only `assets.list/info/scan` and tests; no USD parser or import, metadata marked unavailable. Register and document read-only bridge tools with current filtering; use any annotation plumbing already merged, otherwise omit hints honestly.
3. **L (700–1,200):** isolated immutable snapshot/inspection worker, enforcement probes and dependency coverage tests; strict mode only, fail closed; return metadata without loading. Merge independently as opt-in inspection, disabled where isolation is unavailable.
4. **L (500–1,000):** isolated Kit load/import and integration tests, unit/physics reporting, script-control verification; no unsafe fallback. Enable only on verified platform/version combinations.
5. **M–L (400–900):** optional contained multi-file profile and separately enabled authenticated upload, only after coverage and transport design pass review; may be split into two independent PRs. Bridge annotation transport can land separately before or alongside any PR, without depending on PR #4's unmerged state.

## Risks, non-goals and owner decisions

| Decision / open question | Recommendation and risk |
|---|---|
| What trust level and platform first? | Isolated Linux Kit with no network and no secrets; hostile parsers and GPU stack still carry residual risk. If isolation cannot be proven, filename-only discovery. |
| Strict vs multi-file usability? | Strict default; later admin-opt-in contained profile only after dependency coverage and runtime restrictions are verified. Common textured/multi-layer assets and existing unrestricted sessions are not covered initially. |
| Which folders and limits? | Empty default; allow user-configured narrow roots inside or outside the user's project checkout, with identical controls; start with the caps above and measure. Do not commit personal/user assets to isaac-mcp. Broad roots expose filenames/data. |
| Which presets and license? | Start with small openly redistributable fixtures; audit twin workstation and each object independently. Room needs a local licensed copy and cannot bypass network policy. |
| User-trusted existing session? | Recommend manual user-controlled opening for now; consider a separate default-off, explicitly authorized workflow only after owner review, with no claim of isolation or safe fallback. |
| Remote workflow? | Shared mount first; dedicated authenticated, quota-bound upload later. No agent access to unrestricted file built-ins in the curated setup. |
| Unit conversion and physics? | Reject mismatches until verified; report evidence and warnings, never auto-repair physics. |
| Version support and storage? | Prove 6.2 first, then 5.1 if owner needs it; LFS or release assets for large redistributable files after hosting decision. |
| Should scripts run? | No for untrusted assets; a separately designed trusted profile only by administrator decision. |
| Is metadata safe for agents? | Treat as hostile text, cap and escape; prompt injection remains a risk even with formatting. |

**Non-goals:** arbitrary filesystem browsing, root changes by agents, automatic downloading from Nucleus/HTTP, executing asset-supplied scripts, claiming a security sandbox from MCP filters, building complete external projects, silently modifying physics, or changing existing twin tools as part of this plan.
