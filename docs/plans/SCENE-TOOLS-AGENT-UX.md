# Plan: make current scene tools easier for agents

**Status: review and proposal, not shipped.** The [UR5e reference](../TOOLS-UR5E.md) already names all 23 tools; this is not a replacement reference. **Code** below means static inspection of the base revision; **Assumption** means a proposed behavior or a claim requiring a live test. No Kit, bridge, scene, ROS job or recording was started for this review. [Host reference](../TOOLS-HOST.md) documents the gateway and bridge; [generic sim design](../GENERIC-SIM-TOOLS.md) is a draft, not an available scene query.

## What an agent sees

**Code:** `exts/ur5e-dt/ur5e_dt/extension.py` declares the 23 entries in `MCP_TOOL_REGISTRY` and binds each `_cmd_<name>` in `on_startup`. `bridge_binding.attach` registers them under `ur5e_dt`; `mcp/isaac_mcp/server.py`, `_mcp_name`, renders the dot as `__`. A client should `refresh_tools` and verify the selected bridge identity before mutating a stage; `status` can be hidden by filters, so use the host reference's discovery/CLI procedure when needed. Presence of only local tools is not proof Kit is absent.

**Code:** `isaac_mcp_bridge/schema.py`, `field_spec`, interprets type, enum, `required`, `default` and description; `bridge.py`, `get_registered_tools`, sends field specs. `server.py`, `_build_tool_function`, uses types, enums, required/default and the **tool** description, but does not attach individual field descriptions to generated parameters. `toolset.py`, `derive_parameters`/`derive_tools`, offers signature/docstring-derived schemas for another registration style; it does not fix this registry's missing declarations. All twin registry parameters omit `required` and `default` even where handlers require values or have defaults: optional MCP parameters with omitted values are dropped, then handler defaults apply. For example `object_name` and `position` are rejected by `_cmd_set_object_pose` when absent, while the published schema does not require them. `ASSEMBLIES` contains `fmb4`, `jenga` and `fmb_jenga`, but `assemble_objects` and `add_objects` publish only `fmb1`–`fmb3` enums; the host makes those enums `Literal`s. Verify intended support before expanding the MCP enum.

**Code:** Most handlers return dictionaries with `status: "success"` or `"error"`, a `message`, and varying extra fields; `save_scene_state` and `restore_scene_state` descriptions instead promise `result: "success"/"failure"` and save promises `file_path`, while the handlers return `status` and `json_file_path`. They apply `basename` to supplied file paths and save/restore object poses, not the whole stage. Some handlers return tracebacks. `server.py`, `_dispatch`, serializes bridge results as JSON text and returns transport errors as text prefixed `Error:`; consumers must inspect both forms rather than assume a successful transport means scene success. Whether an MCP client displays these as errors depends on the gateway/client; do not assume an MCP `isError` flag from the returned text.

**Code:** `_cmd_play_scene` waits up to 900 iterations (~15 s at 60 Hz) for warmup; `_cmd_add_objects` stops/plays and waits up to 1800 updates (~30 s at 60 Hz); `_wait_for_stage` has a 60 s deadline. `_cmd_start_ros_driver` caps subprocesses at 240 s for `up`, 60 s otherwise; `server.py`, `RESPONSE_TIMEOUT_S`, and `client.py`, `DEFAULT_TIMEOUT`, are 300 s. Loop iterations and updates are not wall-clock guarantees. A timeout or disconnect is not proof the operation was rolled back or stopped. **Assumption:** add progress/operation IDs only after defining cancellation, state recovery and wire compatibility; first tell callers to inspect state before retrying.

## Cross-cutting design

1. **Inspection before mutation (P0/P1).** No current `ur5e_dt` tool lists current stage prims or object names/poses. `get_recording_status` only reports recording and the bridge `status` reports process/registry, not scene state. Recommend first implementing the generic design's bounded read-only `stage.info`, `stage.tree` and `prim.get/find` in a separate `sim` pack, or a small twin-specific `scene_info` if that work cannot land soon. Include stage identity, timeline, default prim, object paths/poses, graph presence, capped counts/truncation and clear no-stage errors. Reuse the generic design rather than invent an incompatible scene tree. **Assumption:** underlying stage/prim APIs had earlier checks recorded in [verification](../VERIFICATION.md#generic-scene-api-validation), but the proposed tools and their behavior are not shipped.
2. **Composability and naming (P1).** Add one explicit `setup_scene(workstation=false, simple_room=false, ...)` with documented defaults, preflight, ordered step results, conflict policy and no implicit reset. Keep existing `quick_start*` names as wrappers with exactly their current defaults/effects until a separately announced migration. Avoid adding a new name for every combination. Graph-specific ROS setup remains an explicit step; do not silently enable it in a generic asset loader.
3. **Schema and errors (P0/P1).** Carry field descriptions from bridge fields into the MCP schema, test required/default/enum and client display, and reconcile declarations with handlers. Since making formerly optional parameters required can break schema-valid clients, introduce it on new/versioned tools or stage with a compatibility notice. Retain existing `status`, `message`, `json_file_path` and other keys; add `code`, `next_action`, affected paths, counts and partial-effect/warning fields. Errors must distinguish invalid arguments, prerequisites, no stage, missing resources, timeouts and partial mutation. Do not include unbounded tracebacks in routine agent responses; keep diagnostic detail in controlled logs. Adopt a consistent MCP-level error signal only through an explicit compatibility-tested protocol change; preserve old text parsing until migrated.
4. **Idempotency and destruction (P0).** Publish per-tool effects and repeat semantics rather than labeling all setup operations idempotent. `delete_objects` and `new_stage` have warnings in their descriptions but no confirmation parameter. The generic draft's `prim.delete` requires `confirm=true` and refuses protected paths; align new safe tools with it. Document that agent-supplied confirmation is not necessarily informed human authorization; applications must obtain any required user approval before invoking the confirmed operation. Do not silently retrofit a required parameter on legacy names.
5. **Long calls (P1).** Document actual waits and client/bridge timeout layers; return progress and a durable operation ID only if the bridge can reliably observe in-flight and completed operations. On timeout report outcome unknown, inspect scene/timeline or driver status before retry, and list cleanup/partial effects; never promise cancellation on disconnect. Test deadlock and update-loop behavior in a live controlled setup.
6. **MCP annotations and token cost (P1/P2).** **Code:** at this base, `bridge.py`, `ToolDefinition` and `get_registered_tools`, expose no annotation metadata; `server.py`, `register_dynamic_tool`, does not forward MCP annotations. PR #4's `origin/feat/host-tool-scoping` adds annotations to the 21 local host tools and local groups, not bridge tools. Design a backward-compatible optional annotation field across definition, registry wire response, gateway and refresh fingerprint/tests, then classify each twin tool by observed effects (e.g. reset/delete destructive, record status read-only). Hints are not a permission boundary. Shorten verbose tool descriptions to purpose, required prerequisites, most consequential side effect and next step; put recipes, topics and long caveats in the reference. Measure serialized tool-list tokens before/after with a named tokenizer and ensure safety-critical warnings remain visible; no current token count is claimed.

## Documentation quick wins and recipes

**Code:** `docs/TOOLS-UR5E.md` already gives parameters, examples and some effects; `docs/TOOLS-HOST.md` explains discovery, identity and built-in trust. Improve them in a future docs-only PR:

- Add a short “discover and verify bridge → build → inspect → operate → reset” recipe, explicitly noting that typed scene inspection is not yet shipped and `run_python` requires a trusted environment. Do not instruct agents to assume a port or start a second Kit.
- Document `add_objects` stop/play and global cooking setting, `delete_objects` stopping timeline and graph removal, reset's unsaved-state loss, scene-state basename/partial results, sync's no-message error, and the workstation/room early-return ambiguity. Give recovery steps for no stage, missing USD, missing objects, ROS publisher and long-call timeout.
- Correct the registry descriptions for save/restore and recording filename; make destructive warnings prominent; expose meaningful parameter descriptions through the gateway in a later code PR. Describe assembly enum mismatch without claiming unavailable values are callable through MCP. Label recipe verification as pending until live-tested.

## PR sequence and validation

Each PR can merge independently once any earlier groundwork is merged; none requires PR #4's unmerged branch. Sizes are rough total changed lines, including tests and docs.

1. **S (100–250), docs/descriptions:** correct return/default claims, concise prerequisites, destructive and timeout warnings, recipes and known no-op cases. Description-only corrections do not change signatures. Run docs check.
2. **M (250–500), gateway schema and annotations:** propagate parameter descriptions and optional bridge annotation metadata; test old/new bridge compatibility, schema refresh, enum and default serialization, and truthful hint mapping. Coordinate with whichever form of PR #4 lands; do not assume its per-server implementation is merged.
3. **M (300–600), honest outcomes:** add structured status details and partial/no-op information to twin handlers, preserve old fields; handle false-success cases with a documented compatibility transition. Off-Kit fakes test schema, envelopes, error mappings and helpers; run host suite.
4. **M–L (400–800), bounded scene inspection:** implement a small read-only generic `sim` slice with docs, caps and no-stage behavior. It is useful independently and provides agent verification for subsequent setup improvements. Live-check actual stage traversal, world poses and timeline.
5. **M (300–600), compositional setup and confirmed reset/delete:** add new tools, retain legacy aliases, explicit effects and confirmations; document migration. Live-check idempotency, repeated/partial calls, physics and destructive paths in a disposable scene.
6. **M (250–500), long operations:** add progress/status only after operation lifecycle/cancellation semantics are designed; live-test timeouts, disconnect and recovery. This can follow independently when infrastructure is ready.

**Not verified here:** actual MCP client display of field descriptions/annotations or errors; runtime scene, ROS, renderer, physics, idempotency, timing, failure recovery and headless behavior. Static code and existing docs cannot prove these. No code or tool changes are made by this plan.
