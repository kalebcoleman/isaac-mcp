## `/scan` root cause

Established afterward, in new Kits on 6.2.0.0 headless PhysX. In the experiments, each "message" means one was received with `ros2 topic echo --once`.

| Case (code as of the run) | `/scan` publishers | Message | Writer runs |
|---|---|---|---|
| Creating session | 1 | yes | not measured |
| Our save, stopped, new Kit | none | no | 0 |
| The same file minus only the `viewportHandle = 2` line | 1 | yes | 188 |
| Stock `Stage.Export` (flatten), new Kit | none | no | 0 |
| Stock `save_as_stage` (root layer only), new Kit | 1 | yes | 182 |
| Rebuild the graph at the same resolution | none | no | 0 |
| Rebuild at 640x480 before any Play | 1 | yes | 175 |
| Student's `Lab3_05` from the home run, new Kit | none | no | 0 |
| The same, stale product deactivated | 1 | yes | 318 |

These results are from 6.2.0.0 and files whose saved state was only the handle. Later fleet runs (PR 70) showed that a raw export also carries a runtime pipeline that deactivating the product does not fix, on every build tried including 6.2.0.0, and that 6.0.0.0 has no `attach_hydra_texture`. So the handle mechanism below is scoped to 6.2.0.0; see [saved LiDAR scenes](../TOOLS-SCENE.md#saved-lidar-scenes-and-scan).

The third row is the proof. Run 8's `IsaacCreateRTXLidarScanBuffer is deprecated` log clue was a red herring: that node belongs to the private product `sim__lidar__create` makes. `Lab3_05` was tested on a copy with only its domain changed, and the lab PC's own copy was not rerun. See [the explanation and fix](../TOOLS-SCENE.md#saved-lidar-scenes-and-scan).
